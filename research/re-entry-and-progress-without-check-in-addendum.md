# Re-entry and Progress Without Check-in Addendum

Date: 2026-10-11
Related source: `research/raw/founder-reflection-2026-10-11.md`
Related framework: `research/micro-mission-framework.md`

## Purpose

This addendum extends the Behavior-Aware Micro-Mission Framework with a specific caution: app inactivity is an ambiguous behavior signal. It may indicate disengagement, friction, lost motivation, technical inaccessibility, changed priorities, or meaningful off-app progress.

The addendum should be used as a research and design bridge. It does not replace the core framework and does not add effectiveness evidence.

## Evidence boundary

The Oct 11 reflection is a founder retrospective and should be labeled as qualitative case material for hypothesis generation. It should not be used as evidence that RingoStrike causes re-entry, maintains motivation, preserves habits, or improves real-world outcomes.

Safe wording:

> A founder retrospective suggested that app inactivity can coexist with continued real-world goal pursuit, motivating a re-entry design hypothesis for future testing.

Unsafe wording:

> RingoStrike helps users return after disruption.

## Framework extension

The existing framework flow remains:

```text
User behavior signal
→ cautious user state interpretation
→ mission adaptation
→ Ringo companion response
→ feedback / reward loop
→ next action
```

For return after inactivity, the framework should explicitly add a context check before adaptation:

```text
Inactivity or return signal
→ acknowledge uncertainty
→ ask optional context / offer skip
→ preserve durable progress where appropriate
→ show one clear next action
→ invite adjustment, tiny mission, or rest
```

## New behavior signal: return after absence

| Behavior signal | Possible meaning | Caution | Candidate response |
| --- | --- | --- | --- |
| User returns after days or weeks of inactivity | renewed interest, practical availability, guilt, curiosity, changed priorities, off-app progress, or accidental visit | Do not infer failure, laziness, abandonment, or readiness for full workload | Welcome back, preserve earned progress, ask optional context, offer one small next action |

## New design concept: Return Mode

Return Mode is a provisional design concept for users who re-open RingoStrike after a meaningful absence.

Return Mode should aim to:

- reduce guilt and re-entry burden;
- separate durable achievements from time-based streaks;
- avoid demanding retrospective logging;
- make it easy to continue, adjust, start small, or rest;
- ask about changed priorities or off-app progress only as an optional reflection;
- show one clear next action instead of a backlog.

Return Mode should not:

- diagnose the user's emotional state;
- imply that inactivity equals failure;
- erase all prior progress by default;
- force the user to explain absence;
- claim that returning proves habit continuity.

## Candidate Ringo language

Safer example:

> Welcome back. I do not know what happened while you were away, and that is okay. Do you want to continue, adjust the plan, start with one tiny step, or rest for now?

Avoid:

> You disappeared. Your streak is gone, so you need to catch up.

Avoid:

> I know you were struggling, but I can fix it.

## Relationship to existing claims

### Claim 2 — Adaptive mission intensity

Return Mode is a candidate adaptation pathway for inactivity followed by return. It strengthens the need to distinguish mission adaptation from proven continuation effects.

Evidence needed:

- user reactions to return screens;
- whether users understand the offered choices;
- whether one-next-action reduces perceived burden;
- whether users feel less guilt or pressure.

### Claim 4 — Streaks, rewards, and progress feedback

The case suggests separating durable progress from time-based streaks. Losing a streak should not erase all evidence of past effort.

Evidence needed:

- whether preserved progress feels reassuring or irrelevant;
- whether streak loss creates avoidance;
- whether users prefer repair, pause, reflection, or restart options.

### Claim 7 — Behavior signals for adaptive support

Return after inactivity is a strong example of signal ambiguity. It should be treated as a prompt for cautious support, not as proof of a user state.

Evidence needed:

- interviews about reasons for absence;
- comparison of app logs and self-reported off-app behavior;
- whether users feel misread by automatic re-entry assumptions.

### Claim 10 — Ethical boundaries

Return Mode must avoid guilt, emotional manipulation, false intimacy, and over-personalized assumptions.

Evidence needed:

- pressure/guilt ratings;
- qualitative feedback about Ringo's return language;
- participant objections to optional off-app progress prompts.

## Measurement boundary

Return Mode can be evaluated in early studies through perceived clarity, autonomy, guilt, pressure, and ability to identify a next action.

It cannot support claims about long-term habit formation unless tested in a longer design with validated habit measures, appropriate comparison, and sufficient follow-up.
